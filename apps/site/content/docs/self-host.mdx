Smaran is one Bun process plus Postgres with `pgvector`. The embedding model runs inside the process on CPU, so there's no external AI service to pay for.

## What you need

- PostgreSQL 15+ with the `pgvector` and `pg_trgm` extensions (Supabase, Neon, RDS, or your own server).
- Bun `1.4.4+`, or Docker.
- About 1 GB RAM for the API process (the model is ~120 MB on disk).

## Option A — Docker Compose

From the repo root:

```bash
docker compose up -d
docker compose run --rm migrate bun run keys tenant:create "My company"
```

This starts Postgres + pgvector, applies the migrations, and runs the API on `http://localhost:8787`. The second command prints your first API key (shown once). The model is cached in a volume, so restarts don't re-download it. Set `POSTGRES_PASSWORD` in your environment for anything beyond local use.

## Option B — Bun directly

```bash
git clone https://github.com/Ayushpani/smaran && cd smaran
bun install

export DATABASE_URL="postgresql://…"          # direct connection for migrations
bun --filter @repo/db db:migrate                # tracked: each migration runs once
bun run keys tenant:create "My company"         # prints the first API key

STORE=supabase bun run apps/api/src/index.ts
```

With Supabase, use the **transaction pooler** URL (port 6543) for the API and the direct URL (5432) for migrations.

## Managing keys

```bash
bun run keys tenant:list
bun run keys key:create <tenantId> "backend"
bun run keys key:list <tenantId>
bun run keys key:revoke <keyId>     # takes effect within 30 s (auth cache)
```

Only a SHA-256 hash of each key is stored.

## Configuration

| Variable | Default | |
|---|---|---|
| `STORE` | `supabase` | `supabase` (Postgres) or `memory` (sandbox, not persisted). |
| `DATABASE_URL` | — | Required for `supabase`. |
| `PORT` | `8787` | |
| `EMBEDDER` | `local` | `local` (free, in-process), `openai` (any `/v1/embeddings` host), `hash` (tests only). |
| `LOCAL_EMBED_MODEL` | `Xenova/multilingual-e5-small` | |
| `MODEL_CACHE_DIR` | `.smaran/models` | |
| `RATE_LIMIT_PER_MINUTE` | `600` | Per API key, per process. |
| `MAX_BODY_BYTES` | `262144` | |
| `CORS_ORIGIN` | `*` | |

Don't change the embedder on a database that already has memories — vectors from different models aren't comparable.

## Operating it

- **Health checks:** `/health` (liveness), `/ready` (database reachable; `503` otherwise).
- **Logs:** one JSON line per request with request id, path, status, latency and tenant. Request bodies, memory text and SQL parameters are never logged.
- **Shutdown:** `SIGTERM` stops accepting connections, drains in-flight requests and closes the pool.
- **Backups:** back up Postgres as usual; every table is primary data except the model cache.
- **Scaling:** recall is an exact search within one user's memories, which stays fast for typical per-user volumes (thousands of memories). Rate limits, voice ingest buffers and live session events are per process — run one API instance, or put a shared store behind them before scaling out.

## Optional Cloudflare workers

`apps/edge-recall` (a KV cache in front of `/v1/recall`) and `apps/reranker-worker` (a cross-encoder reranker on Workers AI) are optional and deployed separately with `wrangler deploy`.
